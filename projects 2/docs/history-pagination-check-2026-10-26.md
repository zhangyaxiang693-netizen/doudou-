# 项目列表分页与保存响应检查

本次优化针对项目数量增长、个人反复覆盖、组内反复覆盖和多人交替编辑。改动已在本地完成，未推送或部署，未操作生产数据库。

## 最终行为

- “我的项目”个人与组列表统一从协作记录读取摘要，每批 20 条；“加载更多”继续取下一批。个人列表同时包含普通项目和复制到个人的独立记录。
- 后台历史记录也分页加载。列表接口最多允许每批 50 条，使用更新时间和记录 ID 双字段游标；相同更新时间的记录仍能继续翻页。
- 初始化只读取用户和组信息，不再下载全部项目快照。
- 打开、复制及后台查看记录时，单独读取该条记录的完整快照。个人详情仍校验所有者；所有登录用户仍可访问组内记录。
- 协作保存只返回本次提交对象的已提交摘要和更新时间。前端按 ID 合并响应，保留其他已加载记录；不会把其他记录的新时间戳当成当前编辑的覆盖基准。
- 覆盖检查使用打开详情时取得的更新时间；保存成功后更新为本次事务提交的更新时间。冲突仍返回 409，保留当前编辑供另存副本或重新打开最新内容。
- 本地历史缓存只存摘要，最多 100 条。这是缓存限制，不是云端记录数限制。
- 覆盖继续更新原版本，不会因反复保存新增版本行。另存为和复制仍会生成独立记录。

## 验证

`pnpm test`，包含通过 `PGLITE_MODULE_PATH` 启用的隔离 PostgreSQL 检查；生产构建 `pnpm build`。

数据库检查覆盖：

- 个人和组记录各 125 条，按 20 条分页完整读取，包括更新时间相同的情况，无重复或遗漏。
- 个人项目连续覆盖 100 次、两人交替覆盖组项目 100 次，两项目合计仍只有两条版本记录。
- 每次协作保存仅返回本次记录，不含快照；测试中的单记录响应小于 1500 字符，未随其他项目数量增长。
- 过期覆盖拒绝、个人权限、事务中途失败回滚、删除后不复活等原有检查仍通过。
- 新 RPC 对 anon/authenticated 不开放执行。

浏览器使用独立本地内存数据与生产构建走查，未连接云端库：

- 个人列表 20 → 40 → 45 条，无重复；最后显示“已全部加载”。
- 组内首批 20 条，切换第二个组后只显示该组的一条记录。
- 打开项目请求完整详情；覆盖保存只提交该条记录，并显示“已保存”。
- 组记录复制到个人时，读取来源详情后只提交副本。
- 后台历史首批 20 条，查看时可取得完整 JSON。
- 缓存未包含快照；最终使用有效页面配置的个人打开、覆盖链路控制台无错误。

这些检查验证功能和数据一致性，不代表生产数据库并发容量或多年运行压测。

## 上线顺序

先在对应生产 Supabase SQL 编辑器完整执行：

`supabase/migrations/202610260001_history_pagination.sql`

该脚本依赖已执行的 `202610250001_history_consistency.sql`。新脚本添加分页索引，以及独立命名的两个 RPC；旧 RPC 保留，执行脚本后旧应用仍可使用原接口。

执行后确认：

```sql
select
  to_regprocedure('public.write_history_project_compact(text,uuid,jsonb)') is not null as project_write_ready,
  to_regprocedure('public.sync_collaboration_changes_compact(text,jsonb,boolean)') is not null as collaboration_write_ready;
```

两项均为 `true` 后，再部署本次应用代码。代码部署不会自动执行数据库脚本。

生产部署后验证真实登录、个人与组内分页、打开、覆盖、复制；用两位真实用户交替打开并修改同一组记录，再确认旧编辑副本的覆盖被拒绝。

列表按实时更新时间排序。加载期间其他人新建或更新的项目可通过刷新从首批重新读取；已显示的记录按 ID 去重。云端记录总数仍受数据库存储与服务配额约束。
